# カレンダー登録・管理ルール

2026-11-10に本人の「松田観劇カレンダー 登録・管理プロンプト v4」を原文確認して復元。個人チャットの出典と原文は、公開リポジトリ外の引き継ぎ資料に保存する。

## 登録内容（本人のv4指示）

- 専用の外部公開観劇カレンダー、Asia/Tokyo。カレンダーIDはCLAUDE.mdを参照する。
- タイトルは `劇団名「演目名」`。東京以外は `（都市名）`、映像・配信・映画・音楽等は内容を示すプレフィックスを付ける（複数可）。横浜など鈍行圏の都市名、内容が自明な名称では不要。テント公演を野外と同一視してプレフィックスを付けない。
- 劇団名がなければ演出家・主催者名で代替し、フェス等は固有名称を使う。演目名がなければ `劇団名 新作公演` で仮登録し、判明後に更新する。
- 原則終日で、終了日は千秋楽翌日の排他的終了日。開演が明確な単発は時刻付きにする。
- 飛び飛びの日程は連続分ごとに分け、公演のない日をまたがない。同一イベントでも会場・時間帯が分かれる場合は別イベントにする。
- 場所はGoogle Mapsが認識する劇場の正式名称、可能なら住所も併記。特設会場は `○○公園, 市区町村` 等にまとめ、座標だけ判明する場合はそのまま。不明・未定は空欄。
- 説明欄のURLはプレーンテキストで記載し、HTMLタグは使わない。特記があれば、受賞・入選、原作・翻訳、周年・特別企画、注目キャスト・コラボ、フェス参加、ユーザー指定メモを追記する。作・演出家名は原則不要（著名人の異色コラボ等は例外）。個人メモは書かない。
- Availabilityは基本free。「チケット取った」「絶対行く」と本人が明示した場合のみbusy。

## 作成・変更（本人のv4指示と現在のツールの対応）

- 登録先とタイムゾーンを明示する。現在のツールでは `calendar_id` と `timezone_str` に対応する。
- 終日は現在のツールの `start_date` / `end_date` に `YYYY-MM-DD` を渡す。時刻付きは `start_time` / `end_time` に `+09:00` 付きの日時を渡す。両形式は混在させない。
- **旧連携との違い**: v4原文は終日に `allDay: true` と `YYYY-MM-DDT00:00:00Z` を指定し、`+09:00` と日付だけの形式を禁止していた。これは旧ツールでのずれ・エラー対策。現在のツールは終日に日付形式を必須とするため、原文の形式をそのまま渡さず、公演日と千秋楽翌日という意味を保つ。
- v4は、場所が判明していれば作成直後に場所をupdateする（追加確認不要）、不明ならupdateしないと指示している。旧連携でcreate時の場所が反映されないことが理由。現連携でも作成後に場所をupdateする。反映確認のため現行手順では読み直す。複数件は1件の作成と場所設定を終えてから次へ進む。
- タイトル・場所・説明の修正はupdate。**日付変更は削除して作り直す**という本人のv4指示を維持する。対象のeventIdを読み取り、日付以外の既存内容を保持して行う。新旧の取り違えや重複に注意する。
- free/busyは現連携の `transparency: transparent/opaque` に対応する。

## 情報取得

- v4ではx.com・Instagramは取得不可として、URLのみ記載し、内容は本人のスクリーンショット等から得るとしていた。取得できない内容をURLや検索断片から推測しない。
- CoRich、Confetti、チケット・ニュース・劇団公式等の一般サイトを確認する。公式が403等で取得できなければ本人に確認する。
- チラシ・スクリーンショットは直接読んで登録情報を得る。

## 後続の指示・未確認事項

- 芸術祭の登録は採用した個別演目を対象とする（DESIGN.mdの後続方針）。提案に会期全体を掲載できることとは区別する。
- 2026-11-10の指示で観劇予定の参加者情報は削除対象、公演本体は残す。新規作成時に本人参加やMeetが付いた事故への対策案として、参加者なし・Meet生成なしを明示して結果を読み直す。現ツールの指定候補は `attendees: []` / `self_attendance: omit` / `add_google_meet: false`。この組合せの新規作成実動作は未検証で、勝手なテスト予定は作らない。
- v4原文に通知設定の指定はない。既存の通知設定や公開範囲を推測で変更しない。
- この復元作業では既存予定のタイトル・説明・日程・予定あり／なしを一括変更しない。
